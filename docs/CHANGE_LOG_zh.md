# 更新日志 Changelog

本文件记录 **Aliment（供养）** 模组的所有重要更新与改动。

本更新日志遵循 [Keep a Changelog](https://keepachangelog.com/zh-CN/1.1.0/) 规范，
且版本号遵循 [语义化版本 2.0.0](https://semver.org/lang/zh-CN/) 标准。

---

## [未发布] (Unreleased)

### 新增
- **发热与随之而来的疼痛现在会显示在状态栏上。** 在此之前，体温对玩家做的一切都是看不见的：虚弱、挖掘疲劳、
  以及画面边缘的抖动都是自己悄悄出现的，想知道自己病得多重，只能去问诊断指令。现在由两个提示来代替，
  它们与原生效果排在同一行。**`aliment:fever`（发热）** 有三档，分别在 **38.5**、**39.5** 和 **40.0** °C 出现；
  **`aliment:pain`（疼痛）** 只有一级，从 **39.5** °C 开始。
  - 这两个效果本身什么都不做：不带属性修饰符、不做逐刻结算，模组里也没有任何地方回读它们——
    虚弱与挖掘疲劳保持原样。自检会断言这一点，并且还会断言发热的档位读出来**高于**它所对照的症状档位，
    这样两套刻度就不可能悄悄并成一套。
  - 发热的三档是另一套刻度，而不是把症状刻度重新切分。`thermalTier` 仍然只有两个发烧档，
    新增的 39.5 中间档不会改变任何施加在玩家身上的东西——它之所以存在，是因为 39.5 值得被说一声，
    哪怕它并不比 38.6 更糟。自检在三个阈值的两侧都钉住了档位，另外还单独要求 39.5 两侧的症状档完全相同；
    一旦这条不再成立，就说明档位已经变成症状，该退回去的是那个中间档。
  - 它们停留在状态栏上的时间，正好等于症状存在的时间，**没有倒计时**。给一个持续时间就会在图标旁边放一个计时器，
    而计时器回答的是错的问题——终结一场发烧的是身体降温，不是六秒过去——因此它们以无限持续时间加上，
    并在体温回落到阈值以下的瞬间手动移除。这也顺手堵上了一个坑：原版在重复施加效果时会保留**更强**的那一档增幅，
    所以一个只会"加上去"的实现，会在体温已经回落之后，让图标还停在 **发热 III**。
  - 两者都是按效果自身的注册 ID 查找的普通效果贴图，因此由新的生成器 `tools/gen_effect_textures.ps1` 绘制，
    并且在四种语言里都有名称。

### 变更
- **CYP3A4 指标改为平滑下滑，而不是跳变。** 香柠檬素过去是酶上的*阶梯函数*，指标只会有五个取值之一，
  而且一旦越过某个阈值，抑制就整档到位。现在它是一条**曲线**：在为它标定的香柠檬素处，活性精确等于标定值——
  什么都没吃时 **85**、两片 **60**、四片 **45**、七片 **25**、八片半 **10**——两点之间则插值过渡，
  所以多吃一片总是再从肝脏多拿走一点，而不是所有变化一次到齐。每一个标定值、以及它对应的每一个香柠檬素节点都没变，
  消失的是它们之间的平台。每一段用 smoothstep，即 `3t^2 - 2t^3`，它的值与斜率在两端都为零，
  因此曲线在每个节点上都是平的，两段相接处也没有折角。超过八片半后保持不变，这仍然是"抑制到此为止"的原因。
  - 自检断言的是**性质**而不是表格，因为一张五个取值的表根本分不出曲线和楼梯：它把整段香柠檬素范围以百分之一片的步长扫一遍，
    要求指标单步的最大变化不超出最陡一段自身的斜率。阶梯函数会直接失败——它在单步内就跳掉 **25 点**。
    与此并列，曲线被钉在它的六个标定点上（包括八片半到上限之间的平台段），并检查全程不会回升、也不会跑出所报告的取值范围。
- **葡萄柚因此把黄连素压得更久。** 指标原先所在的平台没有了，肝脏在剂量中段的运行值更低：一份黄连单独吃下仍约
  **9,400 tick** 清完，而先吃九个葡萄柚片之后现在要约 **20,100 tick**，不再是阶梯函数时的 17,800——是略多于两倍，
  而不是略少于两倍。这个相互作用的形状没变，它据以标定的每一个数字也没变；变的只是它们之间的下降如今是一段斜率。
- **和平难度现在冻结整套系统，只针对血糖的那套按住机制已经删掉了。** 过去和平模式*只*按住血糖，
  理由是血糖曲线是这个模组里唯一会自己扣血的机制。这个理由太窄了：血钾过量、重度感染的败血症及其组织损伤，
  同样会扣血，而没有任何难度设置在拦截它们。所以那个局部机制被删除，和平模式改走创造模式早就用过的那扇门——
  `AlimentSymptoms.isFrozen` 现在是 `player.isCreative || player.level().difficulty == Difficulty.PEACEFUL`，
  一个开关取代两个，因为两个开关对"这个身体到底有没有在被模拟"只会各执一词。
  - 按住机制做到的事它仍然做到，因为模型根本没有推进：和平模式的身体上什么都不动，进食与注射也一样。
    新的是过去**照跑不误**的其余一切：不施加任何效果、不造成任何伤害、不收挖掘惩罚、也不套用疲惫倍率。
  - 模组**已经**挂在玩家身上的东西会被撤下来，而其中三样本来永远都不会自己消失。两个 HUD 指示是无限时长、
    靠手动移除的，所以一个冻结在发热状态的身体会一直戴着那个图标；挖掘惩罚则是**属性修饰符**，自身没有任何生命周期，
    所以冻结在惩罚中的玩家会永远拿着那把变慢的镐子。这两样现在都会在冻结分支里被清除。
    原生效果则**故意留给自己消退**，因为手动清除意味着要猜哪些是模组挂上去的，
    并且会顺手把玩家自己喝的虚弱药水一起抹掉。
  - 管线是删掉而不是留着不用。`tick` 与 `addGlucose` 在接缝两侧——Scala 模型、`AlimentModelBridge`
    以及 Kotlin 门面——都不再收这个标志，所以已经没有任何办法"部分地"推进一个身体，也不存在算出来再丢掉的东西。
    跟着一起拆掉了所有调用点：指令里 `statusLines` 的那个参数与它打印的 `[held: peaceful]` 标签、
    摄入与症状里的两处判断，以及围绕它们写的那批自检。
  - 因此 `/aliment status` 不再打印任何关于"被冻结"的字样，这是一个决定而不是遗漏：读数描述的是**存下来的身体**，
    而被冻结的身体是"没有任何事情在发生在它身上"，不是"它的数字含义变了"。要老实标它就必须标在每一行上，
    那就是一份在解释自己为何缺席、而不是在描述身体的读数。
  - 有一个后果与按住机制时期完全相同，值得直说：*已经*处在崩溃中的玩家进入和平模式后仍然崩溃，
    因为起因和解药是一起关掉的。如今模组在和平模式下已经完全不索要伤害了——它做不到，因为模型没有推进——
    所以让它不至于致命的是 `ServerPlayer.tickRegeneration`：只要生命值未满，它就**每秒回 1.0 点**。
    若关掉 `naturalRegeneration`，这笔账就会反过来，而那是原版的事，不是这个模组的事。
  - 自检现在从两侧都检查这个冻结，因为它里面每一条断言都是负面的——什么都没动、什么都没施加、屏幕上什么都没留下——
    而一个本来就健康的身体会让它们全部通过却什么也没证明。所以夹具的"活着"被单独钉住
    （一次 tick 确实会推动每一条轴，一顿饭确实会抬高血糖），并且在最后把冻结解除，
    以证明模型确实会恢复。

- **每种电解质自身的浓度越高，它自己的排出速率就越快。** 过去每种矿物的流失都是一个固定数字，
  所以一个钠严重超标的身体，丢掉钠的速度和一个健康身体丢自己那份钠的速度完全一样——多出来的部分只能靠喝水冲掉，
  浓度本身说明不了任何事。现在流失量按数值缩放：肾脏处理的滤过负荷就是血里的浓度，于是
  `loss * excretion` 变成了 `loss * excretion * (数值 / 正常值)`。在正常值处这个系数正好是 **1**，
  所以稳态与所有既有标定都原封不动；变的是高的电解质比低的排得快，而且越高排得越快。
  - 每种矿物自己的系数没有动，所以它们离场的先后顺序保持不变——氯和钠最先、镁和钙最后——
    变成浓度相关的只是**速率**。自检断言的是这条正比关系本身而不是一张数值表：它把两个完全相同的身体
    放在不同浓度上一起 tick，要求更高的那一个绝对流失量更大。
- **缺碘要更深才会表现出来。** 参考下限从 0.40 降到 **0.25**，所以碘从正常值掉到硬下限的一半之前，
  玩家**完全没有**任何症状。甲状腺是滞后的响应者，而一个在 0.39 就出症状的"缺碘"，是在对一个几乎没损失什么
  的身体大做文章。甲状腺驱动的一切都读这一个数，所以设定点、缺乏症状与状态读数会一起移动，
  而重度甲减仍然要等到它自己的阈值 0.20。
- **各种碘来源整体减半，耗尽期也拉长了。** 所有膳食来源**减半**——海带 0.05、干海带与生海藻 0.10、
  熟海藻 0.125、海藻碘盐 0.20、农夫乐事海带卷 0.15、切片 0.05——储备从 0.50 掉到 0.05 下限的时间
  从 3 个游戏日变为 **5 个游戏日**，即每天流失 **0.09**。每天两份海带仍然是维持量，一份仍然不够，
  所以这个取舍的形状没有变；消失的是那"漏吃一次也无所谓"的三天窗口。
  - 超量的碘现在会比恒定流失排得更快，且正比于它高出正常值的部分，所以过量排空得更早，
    **同时不会弯曲耗尽曲线**：这一项是按"高出正常值的部分"而不是整个数值写的，这才让"从 0.50 到下限五天"
    仍然是一个精确值。自检把两半都钉住了——从正常值起的恒定五天，以及同样 tick 数下超量比正常储备流失更多——
    因为一个数字无法同时支撑这两个说法。

### 修复
- **`/aliment status` 现在真的会列出每一个指标。** 它的文档写的是*所有生理指标，一次读完*，而它已经偏离这句话很远了：
  整条**血糖链路**——血糖本身、身体自身的胰岛素、以及注射的胰岛素天冬——都不在其中，**肝脏**也不在其中，
  也就是既没有香柠檬素负荷，也没有葡萄柚交互所撬动的那个 CYP3A4 指标。这四个都是模型赖以运行的量，
  而玩家此前没有任何办法看到它们。现在它们都在读数里了：血糖带着它的参考范围标签，肝脏那一对直接印在
  它所清除的黄连素下面，于是"黄连之所以撑得久是因为葡萄柚"能够在一个地方读完，而不是两个地方。
  - 出于同样的原因，另外还有三样东西也没出现：两个新的**提示**效果及其档位，以及**免疫应答闩锁**——
    那个表示身体已经察觉感染的标志。它远在感染载量高到让玩家感到不适之前就会触发，
    也正是"看起来一切正常、炎症却在往上爬"的原因。
  - **状态判定行**则是从另一侧漏了同一件事：处在低血糖崩溃中的身体会被播报成 `healthy`，因为那架梯子从来没问过血糖。
    现在它会问了，而且崩溃档排在电解质失衡之前——它是那架梯子上唯一会自己扣血的状态。
  - 行的拼装被从命令处理器里拆了出来，成为 `statusLines(data)`，理由与血糖仪那条消息相同：让自检能断言
    **命令真正产出的文本**，而不是它自己拼给自己的字符串。这里真正有价值的断言是**完整性**——
    测试读出 `AlimentData` 实际声明的字段，为每一个配上一段只有它那一行才会产出的文本片段，
    并要求每一个片段都出现在输出里。今后往状态里加字段却不在这里加一行，测试会**按名字**失败，
    而不是悄悄漏印——而这正是当初血糖链路消失的方式。（这项检查的第一版是拿字段清单去和另一张字段名清单相比，
    而任何对读数的修改都不可能让它失败——删掉肝脏那一行时它照样全绿。真正让它成为「对读数的断言」的，
    是与返回文本做匹配的那个片段。）
  - 注意 `/aliment set` 目前仍然无法设置血糖、胰岛素和香柠檬素；读数的完整度先于设置器。
